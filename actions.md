# Текущая задача

## Цель
Доработать интерфейс и серверную логику Django-приложения:
- вывести историю заявки на детальной странице заявки;
- вывести историю оборудования на детальной странице оборудования;
- вывести оборудование внутри локации на детальной странице локации;
- добавить бейдж с количеством оборудования у локаций;
- добавить изменение статусов заявки и оборудования с записью в историю;
- добавить создание локации, заявки и оборудования через интерфейс.

## 1. История на детальных страницах

### Детальная страница заявки

На странице детальной информации о заявке нужно добавить таблицу истории заявки.

Таблица должна выводить:
- дата изменения;
- пользователь, внесший изменение;
- старый статус;
- новый статус;
- комментарий;
- файл, если есть.

Источник данных:
- History_Application.

### Детальная страница оборудования

На странице детальной информации об оборудовании нужно добавить таблицу истории оборудования.

Таблица должна выводить:
- дата выполнения или изменения;
- пользователь;
- тип обслуживания;
- описание;
- результат;
- связанная заявка, если есть;
- файл, если есть.

Источник данных:
- History_Equipment.

## 2. Оборудование внутри локации

На детальной странице локации нужно добавить таблицу оборудования, связанного с этой локацией.

Таблица должна выводить:
- название оборудования;
- инвентарный номер;
- статус;
- тип;
- дата ввода в эксплуатацию;
- кнопка или ссылка «Подробнее».

Требования:
- из таблицы должен быть переход на детальную страницу конкретного оборудования;
- учитывать оборудование, связанное с текущей локацией;
- если оборудования нет, показать понятное пустое состояние.

## 3. Бейдж количества оборудования у локаций

На странице списка локаций нужно добавить бейдж с количеством оборудования, связанного с каждой локацией.

Требования:
- если с локацией связано 5 единиц оборудования, показывать бейдж «5»;
- бейдж выводить рядом с названием или в карточке локации;
- количество считать по связи Equipment.location;
- не учитывать дочерние локации, если это не реализовано явно;
- если оборудования нет, показывать «0» или неактивный бейдж.

## 4. Изменение статусов заявки и оборудования

Добавить возможность переводить заявку и оборудование между статусами.

### Для заявки

На детальной странице заявки добавить форму изменения статуса.

Требования:
- статус выбирать из справочника ApplicationStatus;
- статусы не хардкодить;
- после изменения статуса создать запись в History_Application;
- в историю записать:
  - application;
  - user;
  - status_old;
  - status_new;
  - comment, если поле комментария есть в форме;
  - changed_at.

### Для оборудования

На детальной странице оборудования добавить форму изменения статуса.

Требования:
- статус выбирать из справочника EquipmentStatus;
- статусы не хардкодить;
- после изменения статуса создать запись в History_Equipment;
- в историю записать:
  - equipment;
  - application, если есть связанная заявка;
  - user;
  - maintenance_type;
  - description/comment;
  - result;
  - performed_at.

## 5. Создание сущностей через интерфейс

Добавить возможность создавать через интерфейс:

- Location;
- Application;
- Equipment.

Требования:
- создать или доработать create views;
- создать forms;
- создать templates на Bootstrap;
- добавить кнопки «Добавить» на страницах списков;
- после успешного создания делать redirect на detail page созданной сущности или на список;
- формы должны использовать существующие модели и справочники;
- не хардкодить статусы, типы и приоритеты;
- Location должна поддерживать выбор родительской локации;
- Application должна поддерживать выбор локации, оборудования, статуса, приоритета, исполнителя;
- Equipment должно поддерживать выбор локации, статуса и типа.

## Ограничения

- Не менять структуру базы данных без необходимости.
- Не менять models.py, если задачу можно решить через views/forms/templates.
- Не создавать миграции без объяснения.
- Не хардкодить статусы, типы и приоритеты.
- Не использовать старое поле User.type_user.
- Не использовать Building как основную сущность.
- Не ломать авторизацию.
- Не трогать 3D-визуализацию.
- Все действия изменения статуса должны выполняться через POST.
- Удаление и изменение данных не должны выполняться через GET.
- Если нужной модели или поля нет, сначала указать это в результате и выбрать безопасный вариант.
