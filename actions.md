# Текущая задача

## Цель
Доработать организационную логику, профиль, фильтры и ограничения данных:
- запретить выбор департамента из другой организации при создании/редактировании пользователя;
- добавить карточку организации в профиль для ADMIN и CHIEF_ENGINEER;
- выводить в интерфейсе название текущей организации вместо BEXPS;
- добавить фильтр «Мои заявки»;
- для ENGINEER и CHIEF_ENGINEER показывать «Мои выполненные заявки»;
- добавить валидацию диапазонов дат в фильтрах заявок и пользователей;
- добавить переключение между организациями в профиле, если пользователь состоит в нескольких организациях.

## 1. Ограничение департамента организацией

При создании или редактировании пользователя через интерфейс и через Django Admin:
- нельзя назначить пользователю департамент из другой организации;
- список department должен фильтроваться по выбранной organization;
- OrganizationMembership.department должен принадлежать той же Organization, что и OrganizationMembership.organization;
- если передан department из другой организации, должна быть ошибка валидации.

Требования:
- добавить проверку в form/admin form/model clean, если это безопасно;
- ограничить queryset department в интерфейсе;
- ограничить queryset department в Django Admin;
- не допускать некорректную запись даже при прямой отправке формы.

## 2. Карточка организации в профиле

Во вкладке «Профиль» для ролей ADMIN и CHIEF_ENGINEER добавить карточку организации.

Показывать:
- название организации;
- юридическое название;
- ИНН;
- описание;
- статус;
- роль текущего пользователя в организации;
- департамент, если есть;
- должность, если есть.

Требования:
- карточку показывать только ADMIN и CHIEF_ENGINEER;
- ENGINEER и DISPATCHER не должны видеть расширенную карточку организации;
- данные брать из текущей активной организации пользователя.

## 3. Название организации вместо BEXPS

В интерфейсе вместо статичного текста «BEXPS» выводить название текущей организации.

Требования:
- использовать текущую организацию авторизованного пользователя;
- если организация не определена, показывать безопасный fallback, например название приложения;
- обновить navbar/base template;
- не хардкодить название организации.

## 4. Фильтр «Мои заявки»

На странице заявок добавить фильтр:
- «Мои заявки».

Логика:
- при включении фильтра показывать заявки, где executor = request.user;
- фильтр должен работать вместе с поиском и остальными фильтрами;
- фильтр должен быть в modal фильтров заявок;
- выбранное состояние фильтра должно сохраняться после применения.

## 5. Выполненные заявки по ролям

На странице заявок блок выполненных заявок должен работать по-разному:

Для ролей ENGINEER и CHIEF_ENGINEER:
- заголовок: «Мои выполненные заявки»;
- выводить только выполненные заявки, где executor = request.user.

Для ролей ADMIN и DISPATCHER:
- заголовок: «Выполненные заявки»;
- выводить все выполненные заявки организации.

Выполненный статус определять через ApplicationStatus.code="completed".

## 6. Валидация диапазона дедлайна на странице заявок

В фильтрах заявок:
- если deadline_from больше deadline_to, не выполнять некорректную фильтрацию;
- вывести ошибку: «Неверный диапазон дат»;
- ошибка должна отображаться рядом с фильтрами или над таблицей;
- остальные фильтры должны продолжать работать корректно.

## 7. Валидация диапазона даты выхода на странице пользователей

В фильтрах пользователей:
- если date_reception_from больше date_reception_to, не выполнять некорректную фильтрацию;
- вывести ошибку: «Неверный диапазон дат»;
- ошибка должна отображаться рядом с фильтрами или над таблицей;
- поиск и остальные фильтры должны продолжать работать корректно.

## 8. Переключение между организациями

Если пользователь состоит в нескольких активных организациях:
- во вкладке «Профиль» показать список организаций;
- добавить возможность переключиться между организациями;
- переключение должно происходить только после подтверждения в Bootstrap modal;
- после подтверждения сохранить выбранную организацию как текущую;
- предпочтительно хранить текущую organization_id в session;
- все views должны использовать текущую организацию из session, если она есть и пользователь имеет active membership в этой организации;
- если session organization_id невалидна, fallback на первую активную организацию.

Требования:
- нельзя переключиться в организацию, где у пользователя нет active OrganizationMembership;
- после переключения перенаправить обратно в профиль или на dashboard;
- название организации в navbar должно обновляться после переключения.

## Ограничения

- Не использовать JWT.
- Не использовать User.type_user.
- Роль брать только из OrganizationMembership.role.
- Не показывать данные других организаций.
- Не ломать 3D-визуализацию.
- Не менять структуру базы данных без необходимости.
- Не создавать миграции без объяснения.
- Все изменения организации выполнять через POST.
- Переключение организации не должно давать доступ к чужой организации.
- Если невозможно реализовать через текущие helpers, доработать helper текущей организации.
